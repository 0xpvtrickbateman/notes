CDAO Target Data Architecture & Harness Context Layer
Interactive teaching page for federal staff and contract teams. It shows how source systems, governed data products, Databricks, and the CDAO harness/context layer fit together without treating the harness as a new system or security control.
Pre-decisional mapping. Any production AI, app, retrieval, or automation capability requires the appropriate USCIS/OIT governance, security, privacy, and approval path. This page intentionally avoids case-level PII/SPII and internal endpoints.
How to use this page: select a diagram label or use the index below to jump to a teaching card. This page avoids JavaScript because many Confluence HTML macros strip scripts or advanced styling.
Diagram detail index: Source systems · eCISCOR · Semantic/metadata · Transformation · ODS/serving layer · Data products · Harness · Consumption paths · Feedback loop
How to read this
The left side shows the move from today’s source-system pattern toward a governed hub-and-spoke model. The right side shows how governed products are consumed through Genie, SQL, Python, documentation, prompts, and future assistants.
What the harness adds
The harness is the reviewed context layer: definitions, caveats, approved counting/metric logic, example questions, strong-answer examples, and stewardship review. It improves interpretation; it does not replace platform governance.
What stays governed
Databricks and Unity Catalog remain the governed platform layer for access control, lineage, audit, data discovery, row filters, column masks, governed views, functions, and approved policies. The harness should document context; technical enforcement belongs in approved platform assets.
Databricks alignment: what this page can safely say
This section keeps the architecture grounded in current Databricks platform capabilities while separating platform capability from USCIS approval, configuration, and implementation decisions.
Genie Spaces
A Genie Space is a domain-specific natural-language interface over curated Unity Catalog data. It can return SQL-backed results, tables, and visualizations when the space is well-curated with datasets, metadata, example SQL, business semantics, and instructions.
Unity Catalog governance
Unity Catalog is the Databricks governance layer for data and AI assets. It supports centralized access control, lineage, auditing, data discovery, and fine-grained controls such as row filters and column masks. Those controls are the enforcement layer, not the plain-language harness.
Good Genie setup
Keep each space focused. Databricks guidance recommends limiting the number of tables where possible, using curated views or metric views for complex domains, adding example queries, adding plain-text instructions, and maintaining a knowledge store with table descriptions, join relationships, and business expressions.
Future integration path
Databricks supports Genie APIs and Databricks Apps patterns for natural-language analytics, but this page does not claim they are approved, deployed, or available for this use case. Any production app, API, agent, retrieval, or automation path requires USCIS/OIT governance, security, privacy, FedRAMP/ATO, and funding approval as applicable.

Source systems — C3, ELIS, GLOBAL — plus adjacent identity sources in UDS context
The source mockup keeps the source side simple with C3, ELIS, and GLOBAL. The broader DSSS3 context adds adjacent identity/profile sources such as ADIS, CPMS, and CIS2 for UDS/person-centric work. Keep the main diagram simple, then use the detail notes to explain the larger ecosystem when needed.
C3 / CLAIMS3 — Legacy benefits case-management source; status should be confirmed before labeling decommissioning
Use C3 as a source-system example, not as a confirmed current-state claim unless the appropriate system owner validates the exact transition/decommissioning wording.
ELIS / ELIS2 — Electronic Immigration System; key online benefits source
ELIS appears as a source in the architecture mockup and in the DSSS3 context. Product-line status is time-sensitive, so do not use old on-hold/active status screenshots as current without validation.
GLOBAL — Asylum tracking source; modernization of RAPS/APSS context
GLOBAL is shown as one of the major upstream sources. It is useful for explaining asylum/refugee-related context, but keep detailed protection/confidentiality logic outside the public-facing diagram.
eCISCOR / DBIS — Enterprise Citizenship and Immigration Services Centralized Operational Repository
eCISCOR is maintained by DBIS and aggregates operational source data for analytical use. In this map it is shown as the consolidation hub, but the relationship between eCISCOR, ODS, and the future consumption service still needs architecture-owner confirmation.
Semantic / Metadata layer — Collibra / Alation + Unity Catalog metadata
This is where business definitions, lineage, synonyms, data tags, and approved logic should live or be referenced. The harness should reuse this context rather than inventing definitions inside one prompt or one page.
Transformation & Standardization — Where raw source data becomes usable governed information
This is the place for standard fields, canonical terminology, data quality checks, RefDaaS alignment, and form terminology harmonization. A key example from the context package: forms use different labels for similar ideas, so a canonical mapping is needed before analytics scale.
ODS / Consumption Service — Curated serving layer for governed reporting and analysis
Use neutral wording until confirmed: “serving layer” or “ODS / consumption service.” Avoid claiming eCISCOR is already the true ODS unless validated.
Sharing / external access boundary — Policy, DSA, privacy, and access approval dependent
Sharing belongs in the architecture because the source mockup included it, but keep it visually small. The important point is that external sharing is governed by agreements, policy, approvals, privacy/security controls, and curated datasets.
Governed data products — Reusable, stewarded outputs such as NPD, GDS products, dashboards, marts, and curated views
This is the bridge between Data Management and Data Analytics: Data Management helps make trusted products; Data Analytics helps ensure questions, caveats, interpretation, and adoption are useful.
CDAO Harness / Context Layer — Reviewed definitions, caveats, examples, approved counting/metric logic, and answer expectations
The harness improves interpretation. It is not a new database, not a system of record, not a security bypass, and not automatic enforcement by itself. Where logic must be enforced technically, use approved Databricks and Unity Catalog assets such as governed views, metric views, Unity Catalog functions, permissions, row filters, column masks, and validated examples.
Consumption paths: Genie + SQL/Python — Natural-language and power-user paths should use the same reviewed context
Genie, SQL, and Python users should not interpret the same data product differently. The harness page gives them a shared reference point while Databricks and approved data governance controls remain the control point.
Feedback, benchmarks, and monitoring — The improvement loop after V1
Use benchmarks, validated examples, data-quality checks, user feedback, usage monitoring, and DBU/cost monitoring to improve the harness and data products over time. Databricks supports Genie testing/benchmarks and Unity Catalog data-quality monitoring patterns, but the specific USCIS implementation path must be approved.
Portfolio alignment
This architecture supports the four CD&A/OCDO portfolio lanes captured in the project context package:
  • Data Request Management: Streamline intake and issue resolution; support high-priority requests, data sharing, SNOW tracking, and response metrics.
  • Data Governance: Stewardship, data standards, GDS governance framework, Zero Trust tagging, privacy review, sharing governance, and quality by design.
  • Data Enterprise Products: NPD, GDS, dashboards, RNA, E22, DBIS product ownership, and the reusable governed data products that feed consumption.
  • Data Project Management: Standardized PM practices, communications/change management, FY26 priority planning, and proactive ICE/CBP engagement.
Responsible AI / governance guardrails
  • Humans remain accountable for AI-assisted outputs.
  • AI should not be the sole performer of final high-impact, benefits, enforcement, or other inherently governmental decisions.
  • PII/SPII use requires privacy review and appropriate controls.
  • AI-created records may require records-retention handling.
  • New AI use cases should follow the IT Demand Management / USCIS approval path and OPQ documentation pattern.
