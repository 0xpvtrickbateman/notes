Why we are here

The harder question: can it answer with the right meaning, limits, and reviewability?

Without shared context

06 / 23
The difference it makes

Why a harness matters

The same words can mean different things without context. Flip the switch.

“Why did workload change this month?”

“Workload increased this month.”

May be true — but it misses the definition, comparison period, workload mix, reporting lag, and caveats.

“Under the approved definition, the metric changed. Before interpreting, check the date window, form mix, refresh timing, and known caveats.”

Same question — now grounded in the approved definition, with caveats surfaced up front.

The goal is not to replace the analyst. The goal is to make the first answer safer, clearer, and easier to review.

08 / 23
The build

How to build a harness

Six practical steps — no overengineering required.

1 Pick one use case

One familiar, low-risk data product or dashboard question.

2 Name the reviewers

A data steward plus an analytics validator.

3 Write the meaning

Definitions, caveats, scope, owners, refresh timing.

4 Add examples

Good questions, bad questions, strong-answer examples.

5 Test it

Ask 10 benchmark questions; compare expected answers.

6 Version it

Store, review, revise, and reuse the playbook.

Output: one reviewed harness page + benchmark questions + a decision on what to scale.

Core concept nº 2

What is a skill.md file?

A reusable recipe for one kind of work. Hover any line for the why.

explain_metric_change / skill.md
---name: explain_metric_changedescription: Use when asked why a metric changed.---
Before answering:1. Confirm the metric and data product.2. Read the approved definition from the harness.3. Compare the same date windows.4. Check lag, mix, and known caveats.5. State confidence and next check.
Never make adjudicative decisions.

PLAIN-ENGLISH DEFINITION

A skill.md file is a small Markdown instruction file that explains how to perform one specific task consistently.

It can be used by people, AI assistants, or future app workflows.

It is not automatically a Databricks feature unless connected to an approved workflow.

The harness says what the world means. The skill says how to do one job in that world.

11 / 23
Keep them straight

Harness vs. skill.md

They work together — but they are not the same thing.

Harness = shared world model

Defines the data topic.

Approved terms, caveats, data-product scope, examples, owners, benchmark questions, and answer expectations.

Best analogy: a guidebook or operating manual.

skill.md = task recipe

Defines one repeatable job.

Trigger, steps, quality checks, guardrails, and completion criteria.

Best analogy: a recipe card or SOP.

Together: the harness gives the assistant context; the skill gives the assistant process. The harness sits one level up — it owns the skills for its domain.

What a harness looks like on disk

A small, versioned folder in USCIS GitHub — changed and reviewed like code. Click any file.

uscis-cdao / harness
harness/one domain = one harness
├─ harness.mddefinitions, caveats, answer rules
├─ data-products.mdapproved tables + named owners
├─ examples/good and bad Q&A patterns
├─ skills/task recipes owned by this domain
│    ├─ explain_metric_change/skill.md
│    └─ clarify_data_request/skill.md
└─ CHANGELOG.mdwho approved what, and when

Where it lives

A standard Git repository in USCIS GitHub. Versioned, searchable, access-controlled — one repo per harness.

How it changes

Pull request + named reviewers — the same way code changes. Git history is the audit trail; no side edits.

How it reaches Databricks

Synced into the workspace with Git folders. Genie instructions, prompts, and app configs are derived from it — the repo stays the source of truth.

Plain Markdown in ordinary Git — nothing exotic. Reviewable by anyone, owned by named people.

One level up

Where do skills live?

The harness owns its domain skills; one shared library serves every harness.

Inside the harness — domain skills

Skills that depend on this domain’s meaning live in that harness’s skills/ folder — versioned, reviewed, and released with it.

e.g. explain_metric_change · clarify_data_request

Shared skill library — general skills

One separate, vetted repo of general-purpose recipes — documentation, intake, release notes — referenced by any harness that needs them. Community and vendor skills enter here after review.

e.g. write_release_notes · polish_documentation

You decide — where does each skill live? Pick a skill to test the rule.
“Do all skills live inside a harness?”

No. Only domain-bound skills do. General skills live in the shared library and are referenced — never copied.

“Can two harnesses use the same skill?”

Yes — from the library. A skill exists in exactly one place, and meaning always stays with the harness.

One question decides: does the skill depend on this domain’s meaning? Yes → it lives in the harness. No → it lives in the shared library.

Worked example

Example skill: clarify a data request

How a skill file helps before any SQL is written.

clarify_data_request / skill.md
---
name: clarify_data_request
description: Use when a request is ambiguous.
---
Goal: reach shared understanding before analysis.

Steps:
1. Restate the request in plain language.
2. Ask for target audience and decision need.
3. Identify metric, date range, grouping, data product.
4. Ask which caveats must be included.
5. Stop when the request is a clear task.

Output: short problem statement + open questions.

Why this matters

Many AI failures start before the model answers: the question itself was unclear.

How it helps the contract

Capture requirements faster, reduce rework, and turn meetings into usable artifacts.

How to measure value

Fewer clarification cycles, faster handoff, reduced rework, better first-draft quality.

Access

Unity Catalog, permissions, row filters, column masks, approved data products.

Meaning

What does the answer mean?

Harness, semantic definitions, metadata, examples, caveats, benchmark questions.

Action

What can AI do next?

skill.md, workflow rules, human review, records handling, approval path.

Which data product, dashboard, or use case goes first?

A good pilot is valuable, low-risk, and familiar to reviewers.

Name reviewers

Who validates definitions, caveats, and strong-answer examples?

The harness should be owned by a review process, not one author.

Set success criteria

Less rework, faster onboarding, safer first answers, clearer metrics.
